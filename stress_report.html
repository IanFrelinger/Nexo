Structural compliance is 100% reliable

Every single tier — trivial through hardest — correctly implemented all 6 required IEventReader overrides and targeted the actual CustomEventReader contract. The compiler-driven extraction step (deterministic, Docker) never failed. Whatever the local model's limits, the mechanical scaffolding around it never broke.

Complexity and quality did not correlate the way expected

The two simplest fixtures (T1 trivial counter, T2 fixed-record log) scored worst on referencing the real API — the model echoed the bare template almost verbatim instead of integrating. Meanwhile T4 (variable-length TLV) and T9 (chunked/compressed, private internals) — both objectively harder — got clean 3-of-3 integrations. T1 is arguably an unfair fixture (it's not file-based at all, a genuine mismatch against the path-based contract), but T2 has no such excuse — a real regression on an easy case, most likely small-model variance rather than a real difficulty signal.

Real hallucination observed once

In T9's otherwise-good draft, can_resume() referenced fileproc::MAX_CHUNKS — a constant that exists nowhere: not in the extracted parser, not in the target contract. It would fail to compile. This is exactly the failure mode the system prompt tried to prevent ("never invent methods, fields, or types") and didn't fully succeed — a concrete argument for always compiling the draft before trusting it, not just eyeballing it.

bool can_resume() const override {
  return chunkedTraceLog_.currentChunk() < fileproc::MAX_CHUNKS;
}  // MAX_CHUNKS does not exist anywhere in the source or the contract

Two-class indirection is a genuine failure mode

T5 (SessionLog owns the file; the real read/seek API lives on a separate SessionCursor object obtained via openCursor()) produced a bare template with zero references to either class — the worst symbol score of any tier (1/4). Unlike T1/T2's likely-variance failures, this looks like a real capability limit: a small local model reasoning about a two-hop object relationship rather than a single class's direct API.

Operational fragility under memory pressure

Mid-run, the WSL environment's Ollama service crashed under memory pressure (a 6GB model in a memory-constrained VM, heavy swapping observed) and systemd auto-restarted it — the two tiers running at that moment failed with connection errors and needed a rerun; every other tier succeeded on the first attempt. On resource-constrained hardware, expect this pipeline to need retry logic around the adaptation step, not just the extraction step.
