### The `AddCertificationGate` defect, stated precisely

`AddCertificationInfrastructure(recordStorePath)` correctly selects a
`FileCertificationRecordStore` when given a path. `AddCertificationGate()`
takes no path and calls `AddCertificationInfrastructure()` with none, which
registers `InMemoryCertificationRecordStore` via `AddSingleton` — *not*
`TryAddSingleton`. Because last-registration-wins for `GetRequiredService`, a
host that composes durability first and the gate second:

```csharp
services.AddCertificationInfrastructure(recordStorePath: "/var/lib/ashlar/records");
services.AddCertificationGate();   // silently reverts the store to in-memory
```

ends up in-memory with no error and no warning. The XML docs on
`AddCertificationInfrastructure` describe exactly the failure this produces
("fatal for the CLI, where each invocation is a fresh process") while the
adjacent method reintroduces it.

**FIXED** (this branch). `AddCertificationGate` now takes and forwards
`recordStorePath`, and the rule is *explicit beats default in either order*:
the in-memory fallback is registered with `TryAddSingleton` so it cannot
displace a durable store, and an explicit path calls `RemoveAll` first so it
wins over a default already present. TryAdd alone would have fixed one
composition order and broken the other, moving the silent failure rather than
removing it, so `CertificationStoreCompositionTests` pins both directions. The
signer is now `TryAddSingleton` too — it had the same defect, and there the
silent loss is a host's real HMAC key reverting to the committed dev key.

*Caveat:* no .NET SDK was obtainable in the cloud session that made this change
(the environment's network policy denies `builds.dotnet.microsoft.com`), so the
change is reviewed but **not compiled**. CI is the first compiler to see it.

## Read this first

**The hard half is done and the boring half is not — but two of the boring
items are load-bearing rather than cosmetic.** The certification gate composes
end to end in three places, the autonomy loop has genuinely flown in a
container, and the trust primitives are better than most projects this size.
Nothing needs tearing out.

What is missing is the **policy layer that makes the primitives binding**, and
the **act of shipping**. The default deployment still signs certificates with a
constant printed in the public repo; every strong verification is conditional
on a field an attacker can simply omit; revocation documented as permanent is a
dictionary that dies with the process. And not one Ashlar package exists on any
feed.

The sequencing is unusually clean: **three decisions taken in one sitting
unblock seven items**, two medium changes close the largest security hole, and
one unset repository variable stands between today and a stranger running any
of this.

## Critical path, in order of what unblocks the most

> Item 1 as originally written — push `claude/readiness-keepgreen` — is
> actionable **only from the author's workstation**; see the re-verification
> section above. It remains item 1.

1. **[S] Push the branch and open its PR.** Unlocks the first CI execution of
   the readiness gates; ends the single-machine risk.
2. **[XL] Take three decisions in one sitting** (see *Decisions only the owner
   can make*, items 1–3). Unblocks **seven** downstream items across two areas.
   Nothing in trust or wiring can be sized until these are answered, and
   answering late means reworking shipped flags.
3. **[L] Make signatures mandatory.** Still the largest security gap, and now
   unblocked by SPEC-006's acceptance. Two independent pieces:

   - **Retire the `DefaultDevKey` fallback** so an unconfigured signer refuses
     rather than signing with a public constant. Sized precisely: **30
     constructions of `CertificationRecordSigner`, 23 of them with no
     arguments**, across 15 test files plus three non-test sites
     (`FileCertificationRecordStore`, `tools/Ashlar.CertifyBrick`,
     `tools/Ashlar.ExportCertifiedBrick`). Each no-arg site must opt in
     explicitly. **This needs a compiler** — do not attempt it in an environment
     without the .NET 10 SDK.
   - **Close the downgrade.** A require-signature mode so a *stripped* Ed25519
     field is a refusal — and, in the same change, **trusted-key pinning**,
     because `CertificationRecordEd25519.VerifySignature` verifies against the
     public key carried by the record itself. Requiring a signature without
     pinning only forces an attacker to sign with their own key instead of
     stripping, which costs them nothing; shipping the flag alone would be
     false assurance. Pinning needs the trust root SPEC-006 §3 defers, which
     entangles it with open decision 2. Full write-up: limitation 7 in
     `docs/certification-evidence.md`.

   **CORRECTED 2026-08-27.** Neither piece is gated on the identity decision — that framing
   was wrong. And the downgrade is worse than limitation 7 records: the *payload lane* is
   chosen by `if (record.SchemaVersion is null)` and the legacy lane covers no Ed25519
   fields at all, so nulling `schemaVersion` beats stripping the signature. No minimum
   schema version is checked anywhere in the repo. The first fix is therefore a
   **version floor** (SPEC-006 S-5), which is identity-independent and should ship first.
   See limitation 8 and `DECISION-identity-split.md`.
4. **[S] Ship the gate as a verb.** `ashlar certify <brick-dir> --witness <json>`,
   mirroring `tools/Ashlar.CertifyBrick` (61 lines, already does the whole
   flow). Roughly a 130-line command in the established `ComposeCommand`
   template. Per the owner decision of 2026-08-27 it loads user code in-process
   behind an **opt-in flag**, off by default. The `AddCertificationGate(recordStorePath)`
   half of this item is **done** — see the re-verification section.
5. **[L] Cut the release properly:** decide the package set → promote the API on
   the release commit → move `[Unreleased]` under `[0.1.0]` → **rehearse at
   `0.1.0-rc.1` via workflow_dispatch** → set `NUGET_PUBLISH_MODE` → tag.
6. **[L] Ship the loop as a verb,** and prove it in a container against a live
   daemon. The application gate only smokes `--help`, so the container proof is
   what stops a verb that parses but cannot run.
7. **[XL] Fix the two shipped artifacts** — the container image ships four test
   assemblies plus xunit and Moq (259 files / 309 MB); export-native is broken.
8. **[M] Persist revocation** fail-closed. Today a quarantine evaporates at
   process exit and the artifact reloads on next boot. `InstanceLedger`'s
   durability shapes are prior art to copy.
9. **[L] Clear doc and dead-code debt.** Unlocks nothing — it earns its place
   only because the orphan `src/Ashlar.API` tree (15 files, 13 drifted from the
   live copy) is the highest-probability wasted-day trap in the repo. A security
   fix applied to the dead copy would silently never ship.

## Do NOT start with these

Each is seductive and each would burn a session.

- **Writing SPEC-003/004/007/009.** Four kernel files cite specs that do not
  exist. It feels responsible; it is a week that changes zero behavior. Worse,
  writing SPEC-004 means reverse-engineering the admission contract from the
  implementation the citation was meant to justify. The prior question — does
  this repo keep a numbered-spec system at all — is unanswered.
- **Promoting the 910 public API lines.** Looks mechanical, is an irreversible
  stability promise, and must not happen before the package set is decided.
- **Debugging `ashlar export native`.** Stage one is a one-flag fix; stage two
  is not a bug but a design decision about local LLM inference in the bundle.
- **Deleting dead code.** ~2,600 lines of visible progress touching nothing
  anyone can run, two-thirds blocked on product decisions.
- **Building the ledger anti-rollback anchor or key rotation.** The most
  interesting problems here, both blocked on a trust-root design that does not
  exist anywhere in the tree.
- **Pushing a `v0.1.0` tag to get moving.** The pipeline has never executed;
  nuget.org pushes are not atomic; the tag is immutable. Rehearse first.
- **Chasing the four "unmerged" local branches.** All four were checked: all
  landed. Only `claude/readiness-keepgreen` holds unique work.

## Decisions only the owner can make

**Three were taken on 2026-08-27** and are marked RESOLVED below. The blocking
set is cleared; items 4–11 remain open.

1. **RESOLVED — yes, behind an opt-in flag, off by default.** *(May a shipped
   `ashlar` verb build, load and execute code from a user-named directory in its
   own process?)* The codebase holds both stances
   at once: the autonomy layer enforces a containment chain, while
   `BrickCertificationProjectLoader` does `Assembly.LoadFrom` locally. This
   decides the default flag and the sandbox story of every verb below it.
2. **RESOLVED — one identity, 2026-08-27.** Certification signs with the operator
   keypair, implemented by reading `operator.key` in `Ashlar.Infrastructure` and passing it
   to the `ed25519PrivateKeyBase64` parameter that already exists — no new project, no
   `Infrastructure -> Manifest` edge, no new package. Full reasoning, the two rejected
   options, and the sequencing: `DECISION-identity-split.md`. *(Original framing below.)*
   One operator identity or two? Certification records use a dev HMAC plus
   an optional env-var Ed25519 key; manifest/gate/ledger records use a
   file-based keypair under `~/.ashlar/keys`. `Ashlar.Infrastructure` does not
   reference `Ashlar.Manifest`, so the split is structural — and netstandard2.0
   on `Ashlar.Certification.Contracts` rules out moving NSec down.
3. **RESOLVED — ACCEPTED, 2026-08-27.** The banner is flipped and the
   acceptance-conditional language in §6 is gone. S-4 and the missing-signature
   case of S-1 are now recorded as *unmet obligations of an accepted spec*
   rather than drafts, with the S-4 removal scheduled for the release after keys
   ship. Neither is implemented yet — see the two entries below.
4. Does absence of keys keep degrading to unsigned (SPEC-006 S-2), or does
   require-signature become the default? These reverse each other.
5. Which projects ship at v0.1.0? Thirty declare `IsPackable`; ~22 are packed.
6. Does the exported bundle need local LLM inference, and is `PublishSingleFile`
   worth keeping? LLamaSharp ships four AVX builds of the same `.so` names.
7. Should `ashlar-forge`, `game-director` and `release-manager` get behavioral
   gates? Parked across four convergence cycles. Related: should
   `RuntimeStudioAgentSetReader` fail loudly on malformed JSON instead of
   returning an empty agent set?
8. Do the Unity dev command (1,623 lines + 831 of tests) and the four `ext-*`
   commands ship, or get deleted? Both tested, both registered nowhere.
9. Commercial terms — an entity and a licence, or defer/remove the tier before
   first release?
10. Does this repo keep a numbered-spec system?
11. Who owns the `Ashlar.*` package ids on nuget.org, and does that account
    exist? Prefix reservation and the Trusted Publishing policy are
    prerequisites for the release that cannot be done from inside the repo.

- **The unpushed branch** — see the top of this document. The only genuinely
  unique unpushed work in the repo, and unreachable from any clone.
- **Two inherited open PRs, mentioned nowhere else:** #398 (signed content
  claims — real trust-path work, rotting against a moving master) and #395
  (CONTINUITY.md). Three dependabot PRs (#359, #360, #361) are also open.

  nowhere in it: the `NUGET_PUBLISH_MODE` variable, the nuget.org account owning
  the `Ashlar.*` prefix, the Trusted Publishing policy. If the current owner is
  unavailable, a new owner cannot publish and cannot find out who can.

  for NETSDK1191 across the repo returns zero hits, and `NativeBundleTests.cs`
  claims the runtime build is "smoke-tested by the e2e loop" while every e2e

  rediscovered from scratch.

  The only immutable reference points are merged PRs.
